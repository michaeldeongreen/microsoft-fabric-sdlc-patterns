# Consideraciones de gobernanza para CI/CD en Fabric

> Implementación de referencia: https://github.com/michaeldeongreen/microsoft-fabric-sdlc-patterns

Consideraciones para partners y clientes que diseñan la gobernanza en torno a los *pipelines* de CI/CD para Microsoft Fabric. Los temas siguientes se limitan al propio *pipeline* de CI/CD: configuración del workspace, identidades que usa el *pipeline*, protección de ramas, control del despliegue y auditoría. Los controles adyacentes que quedan fuera del *pipeline* de CI/CD (controles de red, clasificación de datos, cifrado, políticas de acceso a datos en tiempo de ejecución) se recogen al final, en «Controles adyacentes gestionados fuera del *pipeline* de CI/CD»: forman parte de cualquier despliegue maduro de Fabric en producción, pero corresponden al equipo de plataforma o de seguridad, no a quien gestiona el *pipeline* de CI/CD.

Esta guía añade controles de gobernanza sobre el patrón de implementación descrito en la [Guía de implementación híbrida de CI/CD](fabric-hybrid-cicd-guide.md). Conviene leer ese documento primero si aún no se dispone de un *pipeline* en funcionamiento.

## Modelo de identidad: elegir la identidad adecuada para cada función

En una solución de Fabric aparecen tres identidades distintas. Confundirlas es una causa habitual de despliegues con permisos excesivos.

| Identidad | Propósito | Creada y gestionada por | Autenticación |
|---|---|---|---|
| **Service principal de CI/CD** | Despliega elementos de Fabric (*Notebooks*, *Semantic Models*, *pipelines*) desde GitHub Actions mediante `fabric-cicd` | La persona propietaria de la aplicación lo registra en Microsoft Entra; quien administra el workspace le concede el rol de colaborador en el workspace de destino | Actualmente un secreto de cliente en los secretos del entorno de GitHub; conviene evaluar la federación OIDC de GitHub |
| **Workspace Identity de Fabric** | El workspace se autentica *hacia fuera* contra ADLS Gen2 protegido por firewall, accesos directos de OneLake, etc. No la usa CI/CD | Quien administra el workspace la crea en la configuración del workspace; Fabric gestiona las credenciales automáticamente | Gestionada por Fabric: no hay ningún secreto que manejar ([Workspace identity](https://learn.microsoft.com/en-us/fabric/security/workspace-identity)) |
| **UAMI de cargas de trabajo en ejecución** | Container Apps, Functions o AKS que llaman a las API REST de Fabric en tiempo de ejecución (no despliegan elementos) | Quien administra la plataforma crea una identidad administrada asignada por el usuario para cada carga de trabajo y cada entorno | Sin secretos: la gestiona Azure ([introducción a las identidades administradas](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview)) |

> **OIDC para el service principal de CI/CD: merece la pena evaluarlo.** La [guía de Well-Architected](https://learn.microsoft.com/en-us/azure/well-architected/security/identity-access#protect-nonidentity-based-secrets) de Microsoft recomienda «evitar los secretos siempre que sea posible». Con [OIDC de GitHub](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/configuring-openid-connect-in-azure), el flujo de trabajo intercambia un token de corta duración emitido por GitHub por un token de acceso de Azure, sin almacenar ningún secreto de cliente en GitHub. La política de confianza de Entra puede vincularse a notificaciones concretas de repositorio, rama y entorno, de modo que un flujo de trabajo de una *feature branch* no pueda asumir el service principal de producción. Esto elimina la rotación de secretos y el riesgo de filtración. La demostración usa secretos de cliente por simplicidad; OIDC es la dirección recomendada para producción.

## Seguridad entre workspaces

Aislamiento de entornos, RBAC y límites de identidad.

| Área | Recomendación |
|---|---|
| Aislamiento de entornos | <ul><li>Un workspace de Fabric por entorno (Dev, Test y Prod), cada uno con su propio ID</li><li>Un entorno de GitHub por workspace (`Test`, `Prod`): los secretos quedan aislados y los de `Prod` no se pueden leer desde una ejecución de `Test`</li><li>Los despliegues condicionados por rama mantienen los entornos aislados: la rama `test` solo puede desplegar en el workspace de Test, y `main` en el de Prod</li><li>Los filtros de ruta sobre `data/fabric/**` y `.github/workflows/**` hacen que un despliegue solo se active cuando cambia algo desplegable (los *commits* que solo tocan documentación o scripts no consumen minutos de CI)</li></ul> |
| Configuración de inquilino (administración de Fabric) | <ul><li>Alguien con rol de administrador de Fabric debe habilitar el acceso de service principals a las API de Fabric en el portal de administración, dentro de la configuración de desarrollador, y limitar el ajuste a un grupo de seguridad específico que contenga únicamente los service principals de CI/CD; nunca a toda la organización ([configuración de inquilino para desarrolladores](https://learn.microsoft.com/en-us/fabric/admin/service-admin-portal-developer))</li><li>Si se usa GitHub para el control de código fuente, hay que habilitar también la integración de Git con repositorios de GitHub, deshabilitada de forma predeterminada ([configuración de inquilino para la integración de Git](https://learn.microsoft.com/en-us/fabric/admin/git-integration-admin-settings))</li><li>Conviene usar el mismo grupo de seguridad para ambos ajustes (acceso a las API de Fabric e integración de Git), para que el service principal no quede autorizado en uno y bloqueado sin aviso en el otro</li></ul> |
| Control de acceso (RBAC) | <ul><li>El service principal de CI/CD recibe el rol de colaborador en su workspace de destino, que es el rol mínimo para que `fabric-cicd` publique elementos ([roles de workspace](https://learn.microsoft.com/en-us/fabric/fundamentals/roles-workspaces#-workspace-roles))</li><li>El workspace de Dev es solo para personas (integración de Git de Fabric); los de Test y Prod son solo para service principals, sin escritura humana</li></ul> |
| Identidad de CI/CD (despliega artefactos) | <ul><li>Un service principal por entorno en producción (la demostración usa uno compartido por simplicidad)</li><li>Cada service principal limitado al rol de colaborador únicamente en su propio workspace: un compromiso en Test no puede alcanzar Prod</li><li>Los secretos del service principal residen en el entorno de GitHub correspondiente; `secrets: inherit` resuelve los valores adecuados en cada entorno</li><li>Las acciones de terceros se fijan a SHA de *commit* completos, como refuerzo frente a ataques a la cadena de suministro</li></ul> |
| Identidad de cargas de trabajo en ejecución (Container Apps, Functions o AKS que llaman a Fabric) | <ul><li>Conviene usar una identidad administrada asignada por el usuario (UAMI), una por carga de trabajo y por entorno. La UAMI es la [opción predeterminada recomendada por Microsoft para sus servicios](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview#managed-identity-types)</li><li>Varios servicios de Azure en un mismo entorno deben tener **UAMI distintas**, salvo que sean instancias replicadas de la *misma* carga de trabajo (por ejemplo, réplicas de alta disponibilidad de un servicio). Cargas de trabajo diferentes (una Function de ingesta y una Container App de informes) no deben compartir UAMI: tienen necesidades de permisos distintas y comparten el radio de impacto ([recomendaciones sobre recursos replicados](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#choosing-system-or-user-assigned-managed-identities))</li><li>El ciclo de vida de la UAMI es independiente del de la computación: se puede crear la UAMI y concederle acceso al workspace de Fabric *antes* de que exista el recurso ([prácticas recomendadas](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#choosing-system-or-user-assigned-managed-identities))</li><li>Conviene aplicar el privilegio mínimo en el workspace de destino: normalmente rol de lector más permisos por elemento (por ejemplo, `ReadAll` sobre un *Lakehouse* concreto), no colaborador</li><li>La identidad asignada por el sistema (SAMI) solo es preferible cuando se necesita atribución de auditoría por recurso, o cuando los permisos deben revocarse automáticamente al eliminar el recurso</li><li>Advertencia: quien pueda desplegar o ejecutar código en un recurso con una UAMI hereda todos sus permisos; una UAMI por carga de trabajo mantiene pequeño el radio de impacto ([advertencia sobre prácticas recomendadas](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations#consider-the-effect-of-assigning-managed-identities-to-azure-resources-andor-granting-assign-permissions-to-a-user))</li></ul> |

## Aprobaciones manuales y procesos de revisión

Controles nativos de GitHub: aprobación de la revisión de código antes de la fusión (PR y protección de ramas), aprobación previa a la ejecución del despliegue (protección de entornos) y un registro de auditoría que cubre ambos.

| Área | Recomendación |
|---|---|
| Comprobaciones de PR para las revisiones (control previo a la fusión) | <ul><li>Exigir PR hacia `dev`, `test` y `main`; sin *pushes* directos</li><li>Imponer una ruta de promoción con restricciones de rama de origen: los PR hacia `test` deben proceder de `dev` y los PR hacia `main`, de `test`. Los PR hacia `dev` no tienen restricción (las *feature branches* entran por ahí)</li><li>Exigir que las comprobaciones de estado se superen antes de fusionar: `check-pr-ready` y `run-tests`</li><li>Exigir revisiones aprobatorias de los propietarios del código (Code Owners) y descartar las aprobaciones obsoletas cuando se suban *commits* nuevos</li><li>La opción «Require conversation resolution before merging» obliga a atender los comentarios de quienes revisan</li><li>Exigir historial lineal o *commits* firmados si el cumplimiento normativo lo requiere</li><li>Restringir quién puede subir cambios a la rama protegida (solo administración o equipo de publicación)</li><li>Esto se configura en GitHub desde Repository Settings → Rules → Rulesets ([*rulesets* de protección de ramas](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). Este repositorio de demostración implementa la política como tres *rulesets* —`Protect dev`, `Protect test` y `Protect main`, que pueden inspeccionarse con `gh api repos/OWNER/REPO/rulesets`— y la restricción de rama de origen la aplica el flujo de trabajo [enforce-promotion-path.yml](../../.github/workflows/enforce-promotion-path.yml), cuya comprobación de estado exigen los *rulesets* de `test` y `main`</li><li>*Nota sobre la demostración:* este repositorio permite que quien crea un PR lo apruebe, para que un acelerador de una sola persona pueda funcionar. En un repositorio empresarial con varias personas desarrolladoras, conviene dejar esa opción desactivada y exigir la aprobación de otra persona.</li></ul> |
| Aprobación previa al despliegue (control previo a la ejecución) | <ul><li>Configurar reglas de protección de entornos de GitHub para cada entorno (Settings → Environments → `Test` / `Prod`)</li><li>Añadir revisores obligatorios: las personas aprobadoras designadas deben pulsar «Approve and deploy» antes de que arranque el trabajo, y la ejecución queda en estado «Waiting» hasta entonces</li><li>Un temporizador de espera opcional (por ejemplo, 10 minutos) da margen para abortar un despliegue no deseado</li><li>Restricción de rama de despliegue: por ejemplo, que solo `main` pueda desplegar en Prod, de modo que aunque alguien suba el archivo del flujo de trabajo desde una *feature branch*, no pueda apuntar a Prod</li><li>El conjunto de personas aprobadoras es independiente de quienes revisan el PR, lo que permite la separación de funciones (desarrollo aprueba el código; operaciones o publicación aprueba el despliegue en Prod)</li></ul> |
| Registro de auditoría e historial de revisiones | <ul><li>GitHub registra cada PR, revisión, fusión y aprobación de despliegue con su autor, marca de tiempo y SHA de *commit*</li><li>El historial de ejecuciones de GitHub Actions muestra quién lo desencadenó, quién lo aprobó, qué se ejecutó, el estado de salida y los registros completos, y puede exportarse para auditoría</li><li>El propio historial de Git es el registro de revisiones: cada cambio en un elemento de Fabric pasó por un PR revisado, y `git blame` o `git log` responden a «quién cambió esto y por qué»</li><li>La reversión se hace revirtiendo el *commit* y fusionando: al PR de reversión se le aplican los mismos controles, de modo que también queda revisado y aprobado</li></ul> |
| Estrategia de reversión (conviene definirla antes de necesitarla) | <ul><li>Revertir el código es la parte sencilla: se revierte el *commit* y se fusiona, con los mismos controles de PR, así que la reversión queda revisada y auditada como cualquier otro cambio</li><li>Los efectos sobre los datos son más difíciles y muy específicos de cada empresa. Conviene analizar con el equipo:<ul><li>Instantáneas o restauración a un momento dado para *Lakehouses* y almacenes antes de despliegues arriesgados</li><li>Si las personas consumidoras aguas abajo (informes, agentes, aplicaciones incrustadas) necesitan una reversión coordinada o basta con revertir el código</li><li>Cómo comunicar las ventanas de inactividad al negocio</li><li>Qué tipos de elemento necesitan un plan de marcha atrás propio más allá de `git revert`: todo lo que modifica datos, no solo definiciones</li></ul></li><li>Conviene probar la ruta de reversión en Test antes de necesitarla en Prod. Una reversión que nunca se ha ejercitado es una esperanza, no un plan</li></ul> |

## Gobernanza y cumplimiento

Correspondencia entre los controles anteriores y las tres exigencias habituales de gobernanza: auditoría, separación de funciones y estándares corporativos.

| Área | Recomendación |
|---|---|
| Requisitos de auditoría | <ul><li>El historial de Git es el sistema de registro de qué cambió, cuándo y por quién: cada edición de un elemento de Fabric es un *commit* revisado y aprobado</li><li>El historial de ejecuciones de GitHub Actions recoge quién desencadenó cada despliegue, quién lo aprobó (protección de entornos), el estado de salida y los registros completos, conservados según la política de la organización</li><li>Las conversaciones de los PR, las aprobaciones de revisión y los eventos de fusión quedan marcados con fecha y hora y son auditables (sujeto a la configuración de retención y gobernanza de la organización)</li><li>Esto cubre el registro de auditoría del *pipeline* de CI/CD. La auditoría de actividad en el workspace (quién *accedió* al workspace y qué hizo dentro) se gestiona fuera del *pipeline*: véanse los controles adyacentes más abajo</li></ul> |
| Separación de funciones | <ul><li>Quien escribe el código no puede aprobar su propio PR: cuando se configuran aprobaciones obligatorias, GitHub lo impone a nivel de plataforma</li><li>Quienes revisan los PR y quienes aprueban los despliegues pueden ser personas o equipos distintos (desarrollo revisa el código; operaciones o publicación aprueba los despliegues en Prod mediante la protección de entornos)</li><li>La autoridad para desplegar y la autoridad para conceder accesos están separadas: el service principal colaborador de CI/CD no puede conceder roles de workspace, solo pueden hacerlo los roles de administrador o miembro. Lo mismo se aplica a la UAMI de ejecución: el service principal de despliegue no puede concederle acceso a Fabric</li><li>Los workspaces de Test y Prod son solo para service principals (véase la fila de control de acceso): las personas no pueden escribir directamente, solo mediante un flujo de trabajo de despliegue aprobado</li><li>El service principal no puede subir cambios al repositorio: el `GITHUB_TOKEN` del flujo de trabajo está limitado a `contents: read` y el service principal no tiene credenciales de Git</li></ul> |
| Estándares corporativos de gobernanza | <ul><li>La política de ramas impone la ruta de promoción: nada llega a Prod sin pasar por `dev` → `test` → `main`, con revisiones y aprobaciones de despliegue en cada etapa</li><li>Las reglas de protección de entornos pueden exigir personas aprobadoras de un equipo concreto de GitHub (por ejemplo, `@release-managers`), lo que da a la función de gestión del cambio un control estricto</li><li>El temporizador de espera opcional crea una ventana para abortar antes de que los cambios lleguen a producción</li><li>El archivo CODEOWNERS impone los límites de propiedad: las rutas sensibles (por ejemplo, la configuración de producción o `parameter.yml`) se dirigen automáticamente a sus propietarios para revisión</li><li>Todos los controles residen en configuración versionada (protección de ramas, entornos, CODEOWNERS), de modo que son auditables y reproducibles entre repositorios</li></ul> |

## Controles adyacentes gestionados fuera del *pipeline* de CI/CD

Estos controles van más allá del *pipeline* de CI/CD, pero forman parte de cualquier despliegue maduro de Fabric en producción. La combinación adecuada depende del perfil de riesgo, la posición regulatoria y las licencias: algunos controles (por ejemplo, Microsoft Purview, las claves administradas por el cliente o los vínculos privados) requieren SKU concretos de Fabric, Microsoft 365 o Entra ID, y pueden no estar disponibles en todos los inquilinos. Se recogen aparte porque corresponden a los equipos de plataforma, seguridad o protección de la información, no a quien gestiona el *pipeline* de CI/CD. Conviene plantearlos pronto para que las personas especialistas adecuadas puedan dimensionarlos y asumirlos antes de llegar a producción.

| Área | Qué plantear al equipo responsable |
|---|---|
| Controles de red | El acceso a nivel de inquilino puede reforzarse con el [acceso condicional de Microsoft Entra para Fabric](https://learn.microsoft.com/en-us/fabric/security/security-conditional-access) (MFA, IP, cumplimiento del dispositivo) y con [vínculos privados](https://learn.microsoft.com/en-us/fabric/security/security-private-links-overview) para bloquear el acceso público. Para ADLS Gen2 tras un firewall, véase [Trusted Workspace Access](https://learn.microsoft.com/en-us/fabric/security/security-trusted-workspace-access). |
| Cifrado y residencia de datos | OneLake [cifra los datos en reposo de forma predeterminada](https://learn.microsoft.com/en-us/fabric/security/security-fundamentals#data-at-rest). Para cargas de trabajo reguladas, conviene evaluar las [claves administradas por el cliente en el workspace](https://learn.microsoft.com/en-us/fabric/security/workspace-customer-managed-keys) y las [capacidades multigeográficas](https://learn.microsoft.com/en-us/fabric/admin/service-admin-premium-multi-geo). |
| Auditoría a nivel de workspace | La actividad del workspace de Fabric (acceso a elementos, cambios de uso compartido, asignaciones de rol) se registra en el registro de auditoría unificado de M365 y se consulta desde el portal de Microsoft Purview. La retención y el acceso por API dependen del nivel de licencia de M365 y auditoría ([seguimiento de la actividad de los usuarios](https://learn.microsoft.com/en-us/fabric/admin/track-user-activities)). Conviene contactar con el equipo de cumplimiento o de protección de la información para confirmar qué está habilitado en el inquilino. |
| Clasificación de datos y DLP | Las [etiquetas de confidencialidad](https://learn.microsoft.com/en-us/fabric/governance/information-protection), las [políticas DLP](https://learn.microsoft.com/en-us/power-bi/enterprise/service-security-dlp-policies-for-power-bi-overview) y los [indicadores de gestión de riesgos internos para Fabric](https://learn.microsoft.com/en-us/purview/insider-risk-management-settings-policy-indicators#microsoft-fabric-indicators) los configura el equipo de protección de la información en [Microsoft Purview](https://learn.microsoft.com/en-us/fabric/governance/microsoft-purview-fabric). Un detalle relevante para CI/CD que conviene señalar: las etiquetas de confidencialidad se pierden al exportar a Git ([referencia](https://learn.microsoft.com/en-us/fabric/admin/git-integration-admin-settings#users-can-export-workspace-items-with-applied-sensitivity-labels-to-git-repositories)). |
| Acceso a datos de grano fino | Los roles de workspace no lo son todo: hay que configurar también la [seguridad de OneLake](https://learn.microsoft.com/en-us/fabric/onelake/security/get-started-onelake-security) (concesiones por tabla y carpeta) y la [seguridad por fila, columna y objeto](https://learn.microsoft.com/en-us/fabric/security/permission-model#compute-permissions) en almacenes y *Semantic Models*. Esto corresponde a los equipos de ingeniería de datos, no al *pipeline* de CI/CD. Conviene tener en cuenta que desplegar la definición de un elemento puede sobrescribir las reglas de seguridad incrustadas en él. |
| Refuerzo del repositorio y de la cadena de suministro | Higiene estándar para cualquier repositorio que contenga credenciales y scripts de despliegue: [análisis de secretos de GitHub con protección de subida](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning), [análisis de código con CodeQL](https://docs.github.com/en/code-security/code-scanning/introduction-to-code-scanning/about-code-scanning), [Dependabot](https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts) y [revisión de dependencias en los PR](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-dependency-review). Se configuran a nivel de organización o de repositorio. |
